# Workflow and handoffs

## Setup with real participants

Confirm the adopted mode, current project scope and existing Owners. Reuse named chats when requested; create new user-owned chats only on an explicit human request. Confirm authorized project communication paths among the actual participants. Prior valid authorization persists; it does not automatically extend to unrelated people, projects or devices.

Before moving responsibility, identify in-flight commands and current writers. Keep old evidence and frozen specifications. Hand off outstanding repairs and shared integration duties to a technical Worker. Do not interrupt safe work merely to demonstrate a new structure.

Initialize the local runtime paused. Verify participant identity, role receipt, current binding, source/resource ownership and real authorized delivery. A host accepting a message is not proof that the Worker consumed it. Begin development only within the user's current start authorization; explicit setup-only instructions keep it paused.

## A task is a complete outcome

A small task record should identify:

1. Outcome, original requirement/plan reference and priority.
2. Owner, file boundaries and shared interfaces.
3. Development dependencies and acceptance dependencies.
4. Required validation and evidence destination.
5. Current action or specific wait, plus remaining repair responsibility.

Keep technical facts in the original project record. Router state holds bindings, event identity and delivery cursors. Preserve old frozen specifications; a new dispatch receipt records the applicable version and current start decision.

Use exact file ownership. If two tasks touch a common module, designate one technical writer and a concrete integration path. Other independent work can proceed. A waiting device check does not freeze every file in the project.

## Follow-ups and progress

Known task -> current Worker. New task or cross-task ownership conflict -> Router.

Use compact host snapshots with cursors; inspect detailed public history only for unresolved evidence. Do not infer completion from idle, a final message or the absence of a running command. A Worker reports meaningful outcomes, blocked dependencies and repair needs; routine polling output remains local.

A complete technical task includes its applicable acceptance. Substage success is progress, not a reason to release the binding. A waiting Worker remains in use. Completion and reassignment must not revive a late event for the previous task generation.

Model/tool failure, a user pause and an ordinary dependency wait are different states. Preserve them. Wait for native retries to finish, inspect actions already executed and honor server timing; do not invent an automatic fallback model or indefinite retries.

## Sustained continuation

The technical Owner keeps current readiness declarations in the existing plan/acceptance record. The selector checks references, dependencies and task states; it is not a semantic acceptance authority. Stale labels create an Owner review item, not a claim that work is missing or complete.

Once a full task is accepted, the Router chooses eligible work within authorized scope and capacity. Reuse an available existing Worker. Adding a new chat needs human authorization even if the cap has spare space.

If normal host events are insufficient, the user may authorize one native follow-up in the Router chat. Each run checks current pauses, stable events and the original records. It routes actionable missed work, leaves unchanged waits alone and ends the turn. Record actual wakeup and consumption on the real host.

The setup conversation is temporary. It must not remain the only route for Worker messages after setup is done.

## Completion and control

All applicable project work and required acceptance must pass before declaring the project complete. Technical Owners retain unresolved branches and dependencies. Final code, relevant tests, device behavior, data persistence and performance are separate evidence dimensions where applicable.

When complete, stop the matching follow-up. On a human pause, prevent further dispatch and have active Owners reach their safe stop boundaries. Retain state for later continuation; do not delete databases, replay old sends or resume an independently paused task.
