# Workflow and handoffs

## Setup with real participants

Confirm the adopted mode, current project scope and existing Owners. Reuse named chats when requested; create new user-owned chats only on an explicit human request. Confirm authorized project communication paths among the actual participants. Prior valid authorization persists; it does not automatically extend to unrelated people, projects or devices.

Before moving responsibility, identify in-flight commands and current writers. Keep old evidence and frozen specifications, and hand off outstanding repairs and shared integration duties to their technical Owners. Record the Router's project-level planning responsibility in the current handoff. Honor an explicitly chosen single-chat workflow and current human pauses.

Initialize the local runtime paused. Verify participant identity, role receipt, current binding, source/resource ownership and real authorized delivery. A host accepting a message is not proof that the Worker consumed it. Begin development only within the user's current start authorization; explicit setup-only instructions keep it paused.

## Project-level decomposition

The Router/coordinating chat owns this decision for a project-level goal. Preserve the user's scope and existing acceptance criteria while checking current implementation and entry points. Inspect bounded relevant code or ask a Worker to investigate a specific uncertainty, then decide from the returned facts.

Record the decision in the original task/plan fields.

1. Identify an independently useful deliverable and how its receiver will verify it.
2. Locate the earliest real blocker. Separate implementation inputs from later integration, device or save acceptance.
3. Check mutable state, shared interfaces and actual callers. Define one writer for shared changes and a viable integration order.
4. Compare independent output with the expected handoff/integration cost. Keep tightly coupled changes together or sequence them around a stable interface.
5. Assign remaining acceptance and repair responsibility before dispatch. For an existing unfinished task, record any changed scope and responsibility handoff while preserving its frozen history.

| Current evidence | Decision |
| --- | --- |
| Two changes repeatedly modify the same session state or interface | Keep one Owner for the shared change or complete it before dependent tasks |
| Two screens have independent inputs/write scopes and later need the same device | Deliver independent work packages, then batch compatible device checks |
| Actual callers or the remaining gap are uncertain | Resolve that bounded uncertainty, then let the Router decide the split |
| A delivered package still needs overall device/save acceptance | Retain that scope, its acceptance Owner and release condition in the original record |

Workers plan the details inside their assigned tasks. Facts changing the project split return to the Router, while ordinary implementation and repair decisions stay with the task Owner. Review unchanged waits through their existing records and release events.

## A task is a complete outcome

A small task record should identify:

1. Outcome, original requirement/plan reference and priority.
2. Owner, file boundaries and shared interfaces.
3. Development dependencies and acceptance dependencies.
4. Required validation and evidence destination.
5. Current action or specific wait, plus remaining repair responsibility.

Keep technical facts in the original project record. Router state holds bindings, event identity and delivery cursors. Preserve old frozen specifications; a new dispatch receipt records the applicable version and current start decision.

Use exact file ownership. If two tasks touch a common module, designate one technical writer and a concrete integration path. Other independent work can proceed. A waiting device check does not freeze every file in the project.

## Follow-ups and progress

Known task -> current Worker. New task or cross-task ownership conflict -> Router.

Use compact host snapshots with cursors; inspect detailed public history only for unresolved evidence. Do not infer completion from idle, a final message or the absence of a running command. A Worker reports meaningful outcomes, blocked dependencies and repair needs; routine polling output remains local.

A complete technical task includes its agreed applicable acceptance. A work package scoped for implementation and desktop checks can be delivered under that agreement, with remaining overall device/save acceptance assigned explicitly. Existing unfinished tasks retain their original completion criteria until an authorized responsibility/scope handoff is recorded. A waiting Worker remains in use. Release and reassignment follow the current runtime, preserving event generations.

Model/tool failure, a user pause and an ordinary dependency wait are different states. Preserve them. Wait for native retries to finish, inspect actions already executed and honor server timing; do not invent an automatic fallback model or indefinite retries.

## Sustained continuation

The technical Owner keeps current readiness declarations in the existing plan/acceptance record. The selector checks references, dependencies and task states; it is not a semantic acceptance authority. Stale labels create an Owner review item, not a claim that work is missing or complete.

Once a full task is accepted, the Router checks the candidate's project-level boundary, current dependencies and authorized capacity, then assigns eligible work to an existing available Worker. Adding a new chat needs human authorization even if the cap has spare space.

If normal host events are insufficient, the user may authorize one native follow-up in the Router chat. Each run checks current pauses, stable events and the original records. It routes actionable missed work, leaves unchanged waits alone and ends the turn. Record actual wakeup and consumption on the real host.

The setup conversation is temporary. It must not remain the only route for Worker messages after setup is done.

## Models and Goals

Use current effective settings and user preferences. Review model/reasoning choices at first selection, when task risk or dependency complexity materially changes, when supported settings change, or when the user requests an adjustment. Account for the Router's cross-module planning work as well as Worker implementation difficulty. Unchanged settings reference existing selection and runtime evidence.

Apply authorized changes through supported host parameters. Record the requested settings, tool outcome and actual runtime evidence separately. Missing effective-setting evidence stays unverified and can be completed at a normal handoff when new evidence appears. Continue unaffected authorized work.

Create Goals only when explicitly requested. Preserve unfinished goals, budgets and current human pause instructions. Model settings and Goal state are verified through their respective host capabilities.

## Worker titles

After a Worker actually consumes a new complete-task assignment, the Router synchronizes its sidebar title through the [native title check](runtime.md#worker-titles-follow-accepted-tasks) and reads it back. Keep the project/Worker prefix. Internal steps, waits, repairs and reservations retain that binding's title. Save tool results and readback in the original handoff.

## Completion and control

All applicable project work and required acceptance must pass before declaring the project complete. Technical Owners retain unresolved branches and dependencies. Final code, relevant tests, device behavior, data persistence and performance are separate evidence dimensions where applicable.

When complete, stop the matching follow-up. On a human pause, prevent further dispatch and have active Owners reach their safe stop boundaries. Retain state for later continuation; do not delete databases, replay old sends or resume an independently paused task.
