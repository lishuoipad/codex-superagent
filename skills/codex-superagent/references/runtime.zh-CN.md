# 任务运行时与宿主边界

用于 Router / 完整任务 Worker 模式的接入、检查与恢复。技术工作继续保存在项目既有任务和验收记录中；运行时只保存路由所需的身份、绑定、订阅、控制状态和发送意图；事件来源的读游标由实际宿主维护，不另建一份业务事实账本。

## 职责与容量

Router 只接单、保留原始需求、确定完整任务归属、处理跨任务依赖/冲突并转达结果。技术 Worker 对调查、方案、任务内拆分、实现、接线、验证和返修负责；共享文件仍只有一个技术写者。已知任务后续事件直达 Owner，不让 Router 再审每条技术证据或等待长命令。

独立 Worker 上限来自项目明确授权的配置。计入仍持有未完成任务的 Worker，包括等待、暂停、审批、设备占用和返修中的 Worker；Router 与已完成并释放绑定的历史聊天不计。上限不是目标：例如项目授权 4，最多允许 4 个在用 Worker，不能把它升级为技能全局默认。子智能体使用另外核对真实宿主额度和内部任务边界，既不算同一组独立 Worker 名额，也不因此获得额外额度。

已有未完成任务不能通过改标题、换事件 ID、标记聊天 idle 或提前完成 Goal 释放容量。没有就绪任务时保持等待，不能为占满名额创建工作。新建用户聊天仍须明确授权；配置空位不自动创建聊天。

## 事件投递规则

1. **先核绑定。** 事件含可核对来源、任务版本和目标身份；只使用已授权目标。已绑定任务的跟进、工具完成和依赖变化交 Owner；新需求、越界或归属冲突交 Router。未知归属不广播，不按标题猜任务。
2. **先持久化。** 发送前将事件、目标、任务绑定和发送意图写入自有持久状态，并按同一事件与绑定去重。重复观察、进程重启或读取游标回退不能生成第二份相同派发。
3. **发送前再核。** 核目标宿主/身份、当前绑定、鲜活状态、在途操作及最新停止信号。快照缺失、过期或冲突就不发送；旧缓存不作补救通路。角色授权不等于创建 Goal、改模型或发布授权。
4. **结果分开记。** 已登记、消息已接受、对方已消费和任务有效推进是不同证据。只有明确未发送且再次核对通过才可按原意图处理；超时、断线或结果未知不盲目重发，不用另一工具复制同一消息。
5. **终态与暂停优先。** 迟到事件不重开 completed/superseded 任务。用户暂停优先于交付、手机接入、重启和依赖解除；事件不得自行恢复开发。

流程复用 `SupervisionStore` 的固定 registry、数据库连接和 metadata 基础，路由相关状态写入专属表，不复用原业务 records，也不扣有限监督 run 的通知/恢复预算。它只写自有数据库，不修改 Codex 的聊天数据库。更换目录、重启或重新初始化不能作为丢弃已消费事件或发送意图的方式。已有交付/验收事实按引用读取，路由状态不能取代业务验收。

## 维护完成后保持待命

配置必须显式写 `initialDevelopmentEnabled=false`；初始化后的数据库状态为 `developmentEnabled=false`。当用户明确要求“修改架构后先不开发”，完成角色绑定、持久状态和离线检查后仍保持该状态。可以读取状态、导出必要诊断，不执行真实开发派发；事件可以保留，但不能据此解除暂停。

恢复操作必须提供绑定 Router 的 `actor` 和 `authorization={path,sha256}`，引用明确人类恢复指令，并核对适用范围及先后顺序。脚本校验角色标识与证据字节，不自动判定正文是否来自人类、授权是否充分；真实调用宿主仍须核对身份和指令来源，不能把传入字符串当安全认证。普通助手消息、设备重连、自动化触发、进程重启或旧 Goal 状态都不能成为恢复证据。目标属于暂停的专项任务时，团队恢复也不自动恢复它；须分别核对用户授权。

本地 `pause/resume` 控制团队派发开关；`worker-state` 通过 `actor`、`threadId`、`state` 和 `authorization` 显式控制某个未完成任务的 `active`、`waiting` 或 `paused` 状态。恢复团队不会解除任务自身的暂停；任务恢复同样先核实明确人类授权。暂停和等待者仍计入在用上限，已完成任务不能靠 `worker-state` 复活。

这些本地操作不改变原生 Goal、不启动聊天，也不中断已执行工具。暂停中的已有操作仍按原保存、停止与资源归还规则收口；维护者不伪造 Goal 状态，也不把无 Goal 的聊天自动补成 Goal。

## 本地入口

`task_runtime.py` 使用显式 `--config`。配置的 `schema`、`teamId`、`hostId`、`router.threadId`、`maxInUseWorkers`、`allowedEventSources`、`initialDevelopmentEnabled`、`dbPath`、`registryPath`、`statusPath`、`workers` 和 `authorization` 来自当前获准部署，将团队固定到本机数据库/registry。操作用绝对 `--input` 路径传递不超过 64 KiB 的 JSON，不将真实线程 ID、私有路径或消息正文放入公开示例。

```text
python /absolute/scripts/task_runtime.py --config /absolute/local-config.json init
python /absolute/scripts/task_runtime.py --config /absolute/local-config.json status
```

同一入口提供 `export`、`ingest`、`subscribe`、`assign`、`complete`、`pause`、`resume`、`worker-state` 和 `reconcile`；这些本地状态动作不等于消息已经送达。`complete` 的路由终态不能替代项目验收；`resume` 须由有权宿主核实显式人类恢复证据，不能由事件自动触发。`reconcile` 只在核对原宿主实际历史后处理结果未知的投递，不能用任意有哈希的文件把未知改成未发送。运行前以当前脚本 `--help` 和已审核配置为准；对现有运行保持相同 registry，不删除数据库重建。 事件通过显式 `ingest` 输入；宿主不会自动扫描聊天历史、读取项目全部记录或安装事件采集器。订阅存在不代表对应来源已接通，来源接入另按事实核验。

宿主入口 `task_runtime_host.py` 必须指定绝对 `--config`，并选择互斥的 `--check`、`--once` 或 `--duration-seconds N`（N 为 1–900 秒）；可用 `--codex` 和 `--sock` 显式选择已存在的可执行文件及原宿主控制 socket。`--check` 只读目标加载状态、Goal、队列和后台命令，不发起新轮次，成功也只代表只读接口接通。

实际发送另需绝对 `--verification` 路径。已审阅的小 JSON 回执须将 `policySha256`、`codexPath` 和 `controlSocket` 绑定到本次配置与精确通路，包含 `verified:true`、`exclusiveDispatcher:true` 及 `evidence={path,sha256}`。代码核对字段、路径和哈希；真实权限、证据含义及单一派发者仍由调用宿主核实，不因手填 true 就获得已验证能力。运行期间配置或核验回执字节变化即停止，不隐式采用新值。

默认暂停时，`--once`/有限运行只返回本地暂停状态，不查询或发送原生消息；`--check` 是单独的显式只读检查。缺少原控制 socket 时返回不可用，不启动 daemon、不加载目标，也不 fallback 到队列。有限运行不自动续期，不安装服务、定时任务或后台监控子智能体。

## 原计划接续

`project_continuation.py` 是只读选择器，复用项目原计划、原验收账本和当前任务绑定；不复制业务状态、不发送消息、不创建 Goal 或聊天。项目接线应显式指定授权阶段、当前合同及现有 Owner；技能不把某个项目的阶段名称、Worker 数量或路径变为全局默认。

- **先判断下一步是否就绪。** 开发输入依赖与验收依赖分开。等待手机或整批验收不自动锁住无关开发；已持有未完成任务的 Worker 保持原绑定与计数。已有任务的继续事件仍送原 Owner，不能把每次回访变成新任务。
- **陈旧或未知状态交 Owner 核实。** 旧 `planned` 不证明尚未实现，旧 `complete` 不证明全部验收。优先读取适用范围、实施/验收状态和技术 Owner 在原记录中的有效交付。依赖缺失、相互冲突或未核验时，返回具体核查事项；Router 路由该核查，不代做源码调查。
- **就绪说明仍归技术记录。** Owner 在原计划或账本维护可接续任务、适用依赖、写入范围和证据引用；不要建立第二套验收账本。选择器检查已有字段与引用，Router 按原优先级和实际容量分配。哈希一致只证明字节，不能让选择器或 Router 自动批准技术结论。
- **完整交付触发下一项。** 当前任务满足完成条件并有明确交付后，Router 核对路由绑定及未知发送已解决，释放该任务、选择下一就绪任务并按同一意图投递。发送结果不明时先调和，不重新挑一个事件 ID。没有就绪项时保留待核实/等待原因，不靠不断增加 Worker 维持忙碌。
- **完成要求来自原合同。** 必要功能、适用边界以及材料、行为、桌面、手机、PC 视觉、保存与性能等各维度按项目原标准判定；不适用须有依据，失败和未验证不当作通过。完整项目与子任务完成分别判断，所有聊天空闲不是完成证据。

只读入口：

```text
python /absolute/scripts/project_continuation.py inspect --plan /absolute/plan.json --ledger /absolute/ledger.json --team /absolute/team.json --runtime-config /absolute/runtime-config.json --scope PhaseA,PhaseB
python /absolute/scripts/project_continuation.py next --plan /absolute/plan.json --ledger /absolute/ledger.json --team /absolute/team.json --runtime-config /absolute/runtime-config.json --scope PhaseA,PhaseB
```

`--scope` 仅填人类已授权的阶段；省略时沿用计划原目标，不能靠空闲推断扩展范围。选择器直接读取当前运行时，不以旧导出状态代替。`inspect` 返回就绪项、被拒的声明、Owner 待核项和完成条件；`next` 返回路由建议，既不完成当前任务，也不实际发送。

技术 Owner 在原账本的 `continuation`（`schema:1`）下维护 `readyNextTasks`：每项引用 `taskId`、`mode`（`development/acceptance/review`）、`planUnitSha256`、`reviewedBy` 与 `evidenceRef={path,sha256}`。`inspect` 给出对应计划单元哈希；`planUnitSha256` 和 `planSha256` 均为选择器生成的规范 JSON 哈希，不是原文件字节哈希。已有任务填写 `taskBindingId`，优先级沿原计划；`actionClass` 仅允许开发、验收或核查，发布等外部动作继续核对各自授权。需要明确依赖证据时，`dependencyEvidence` 中注明依赖任务、开发/验收类型、对应单元哈希和证据引用；不能凭一句“依赖已完成”跳过核对。`pausedTaskIds` 用当前计划中的真实任务 ID 保留独立暂停；未知 ID 会报错，不能用猜测的专项名称代替。

完整项目的 `completionReview` 由当前技术 Owner 核实后填写，`reviewedBy` 为该 Owner，绑定当前 `planSha256`、授权 `scopePhases`、`requiredTaskIds` 和证据引用；阶段及任务 ID 顺序沿用 `inspect` 输出。`result=passed` 时仍须无 `remainingRequiredItems`、无 `unresolvedDefects`，必要计划项与子项已通过适用验收，未完成绑定已收口。该结构只记录 Owner 的技术判断，不是另一份独立审计。

就绪声明不是每次回访的催促命令。事件 ID 应稳定绑定任务/绑定版本、计划单元哈希和同一依赖或交付证据；相同事件已接受或消费后不重发。Owner 将已消费且在途、有效等待或已完成的声明移出当前 `readyNextTasks`，在原账本保留消费/等待历史，并只在出现下一可行动条件时补新声明；仅给旧声明加 `status/consumedAt` 不会让只读选择器自动忽略它。Router 保留对应游标。某个已处理候选不能反复占住选择结果、遮蔽其他就绪任务。全部计划项报告验收通过但缺最终复核时，`next` 返回 `request_completion_review`；若仍有未释放任务绑定，返回 `request_owner_closeout`，由 Owner 交付收口证据后处理，选择器不会自动释放。

运行前用当前 `--help` 核对实际参数。选择器的路由建议不是执行权限，不改变原账本的单一写者。

## 原生聊天工具与定时回访

`task_native_delivery.py` 为原生聊天工具维护明确区分的发送意图和回执。它复用当前运行时的 registry/SQLite 身份，不启动 RPC 宿主、不调用模型、不写 Codex 私有数据库，也不自行调用会话中的 MCP 工具。只有实际原生调用方按授权、最新暂停与鲜活目标状态发送后，才能记录工具接受；接收者的回执和实际任务推进另行核验。

原生适配入口：

```text
python /absolute/scripts/task_native_delivery.py --config /absolute/runtime-config.json status
python /absolute/scripts/task_native_delivery.py --config /absolute/runtime-config.json prepare --input /absolute/native-intent.json
```

动作分为 `prepare`（事件、正文与授权引用）、`begin`（同一事件、发送会话 token 与鲜活目标快照）、`finish`（同一 attempt token 的 `accepted/not_sent/unknown` 结果）、`receipt`（正确任务/接收者的消费轮次及证据）和 `reconcile`（Router 根据真实历史调和不明结果）。`status` 用于有界读取。确切 JSON 字段以脚本为准；输入用绝对路径，私有消息与真实身份不放进公开配置。`begin` 返回的原生目标及正文仍须由获授权调用者核对最新人类指令并实际发送，`accepted` 不能写成消费或技术通过。

原生工具路径与 `task_runtime_host.py` 的 RPC 路径分别登记、验证。一个路由流只使用约定的派发者和 provider；不可把同一事件同时交给 RPC 与原生工具补发。持久意图记录目标、任务版本和不确定结果；进程或调用中断后不能将 unknown 自动视为未发送。准备动作、token 或 `before_send` 都不是跨工具发送许可；分开的本地状态检查与 MCP 调用无法原子覆盖期间发生的用户暂停或新输入。

用户明确授权持续接续后，优先使用事件消息；原生定时回访只补漏。复用已有对应回访，在原 Router 聊天保留一个明确目标及停止条件的 heartbeat，不按每个 Worker 创建定时器，也不新建常驻监控子智能体。使用宿主的自动化工具创建/更新，保留用户通知意图，不手写定时配置。涉及本机项目时电脑和桌面应用需要运行；日程存在不代表回访已经实际执行。

每次回访先核对最新人类停止、团队与任务门禁、已有发送意图和有界任务游标；不恢复暂停、不改 Goal、不重复在途工作。只处理新的交付、已解除依赖或已有就绪项，已知任务直达 Owner。没有可行动变化时结束本轮，不重复汇报；完成、失败、明显停滞或需要用户操作时才通知。项目完成后结束该回访；全部工作受阻时报告具体依赖，不循环发送“继续”。

崩溃可能遗留 `inflight`。`status` 保持只读；调用者先核真实原生历史，再对 unknown 或租约已过期的原生 inflight 使用 `reconcile` 记录明确的接受/未发送结果。租约未过期不能接管；无法证明实际结果时保留未决，不能只因超时就改为未发送，也不重置尝试预算或解除暂停。

消息 `not_sent` 的重试只针对明确没有发出的投递；已接受后发生的模型容量故障继续走既有容量恢复规则，不能重发原任务冒充恢复。瞬时模型/网络故障先让宿主重试，遵循返回的等待提示及既定次数/截止时间。发过工具的失败轮先核实际结果；无法确定是否送达就保留 unknown。扩大模型、权限、并发或恢复独立暂停仍须有对应授权。一次真实回访成功只能证明该路径本次可用，不保证机器休眠、网络故障或模型不可用期间始终推进。

上线验证使用不改产品的最小任务，核对交付后接下一项、等待不全队阻塞、重复事件不重做、恢复不重发、暂停阻止后续派发。真实任务再独立核对收到消息、开始工作和必要验收；不以架构探针替代产品验证。

## 宿主能力与角色规则分开

| 层面 | 可以证明什么 | 不能据此宣称什么 |
| --- | --- | --- |
| 角色规则 | Router 与 Worker 被告知各自职责 | Codex 已机器级裁剪 Router 工具集 |
| 受限路由入口 | 入口只开放状态、分配和路由等受限动作 | 普通聊天的全部工具或权限已被全局隔离 |
| 本地测试 | 模拟事件下的计数、暂停、去重和持久意图符合约定 | 当前桌面聊天能在后台收件或自动恢复 |
| 原宿主检查 | 受支持接口可连接且目标在该宿主加载 | 消息已消费或技术任务已通过 |
| 真实受限验收 | 本次指定事件送达正确 Owner 并产生预期结果 | 长期无人值守可靠或所有模式都已验证 |

代码宿主复用 `recovery_rpc` 适配，只连接已存在、已加载同一目标的原生控制接口；接口不可用时保持关闭。不得启动第二个 app-server 加载同一聊天、接管私有 stdio 或用未核实的命令队列绕开边界。`codex queue` 的具体版本可能涉及 Embedded 后端，排队成功不能当作送达原桌面宿主的证据；在原目标加载方式、模型行为及权限未核实前，不作自动 fallback，也不启用 `--resume`。经精确版本和真实宿主验证的队列通路须单独记录能力，不预先认定永远可用或永远不可用。

代码宿主通过 `dispatch()` 在同一数据库事务内完成最终准入、受限原生调用和结果登记，与本地团队/任务暂停提交串行。已经提交的暂停阻止下一次发送；已获准且被原宿主接受的轮次不能被之后的暂停撤回。`claim()` 仅登记在途意图，`before_send()` 只作兼容诊断，二者都不是可拿到另一个工具中使用的发送许可。

原生 API 没有“只在仍 idle 时启动”的原子比较操作，因此仍需核对单一派发者和最新原生状态；本地事务不保证外部 API 恰好执行一次，也不能屏蔽用户输入。发送异常或进程中断后的不明结果保持 unknown，先核实实际历史，不自动重放。

原生聊天工具的投递按该工具自己的授权、最新用户指令和消息证据记录；需要持续接续时使用上文独立的原生工具路径。普通 Python 不能自行调用会话里的 MCP 工具；禁止先取本地 `claim/before_send` 结果、再另行调用消息工具并宣称跨工具原子。手动送达不能记为代码宿主的运行验收，也不能据此宣称本地暂停门已覆盖外部消息发送。

这些实现承接 Router/任务 Worker、持久事件和发送意图的设计，不等于部署了 DeepSeek 原生 Harness。普通 Codex 聊天目前的角色约束仍是指令；工具集合、执行器、订阅与应用事件是否被宿主强制支持，必须分别核实。不要照搬其他 Harness 的无人审批、自动合并或多设备行为；权限和验收继续服从当前项目。

## 验证与交付

必要本地检查覆盖：等待/暂停未完成任务仍计入上限、达到上限拒绝新绑定、已完成历史不占用、已知事件直达 Owner、新需求交 Router、团队与任务各自暂停、团队恢复不解除任务暂停、暂停提交与 dispatch 的先后、旧事件不复活任务、重启不重复发送，以及结果未知停止自动重发。

实际接入后才检查目标身份、事件真实送达/消费和繁忙任务不阻塞无冲突任务。用户要求暂不开发时只做不触发开发的本地/只读检查，交付中明确“架构已改、开发待命、真实执行验收尚未进行”。缺失宿主接口如实报告，不为完成验收启动开发或新后台服务。
